# dsh-academic-research 科研交接规范

包名：`dsh-academic-research`
定位：**保真记录、问题交接、按已定方案执行；压缩不改写任何人说过的话，也不代做科研决策。**

包的最终目标是**一个完整的科研 agent**；当前实现的是其中的压缩后端与 `research-workflow` 技能，
扩展路径见 [`ROADMAP.md`](ROADMAP.md)。本文规定两件事：**压缩后窗口里留下什么**（§1），
以及**研究状态怎么记**（§2–§5）。两者由不同的一方负责，不要混。

## 0. 职责与范围

### 0.1 三种职责，不要求三个 Agent

| 职责 | 应当做 | 不应当做 |
|---|---|---|
| 压缩程序 | 按固定规则从会话日志生成检查点：原话逐字、标明作者、丢弃的内容留指针 | 调用模型改写、挑选或解释任何内容 |
| 执行模型 | 根据明确方案做最小代码改动、运行指定实验、报告实际结果；在事情发生时更新研究状态记录 | 擅改研究目标、评价指标、对照、数据划分或验收标准；把自己的推测写成用户的前提 |
| 决策模型 / 用户 | 判断研究路线、解释结果、确定对照和下一步 | 把尚未运行的方案当作已经验证的结论 |

**范围升级（已确认，分阶段实施）**：产品目标从「保住上下文」升级为「让一个研究问题跨会话、跨模型、跨代码修改持续推进」——问题有依据，决策有记录，实施有边界，结果能追溯，下一步能接着做。四种工作方式：**研究整理**（读材料，整理已知事实、方法条件与信息缺口）、**研究评议**（分析可比性、替代解释、反证与下一步）、**实施推进**（按已确认决定做最小改动与必要验证）、**恢复与交接**（核对真实代码与产物状态，恢复未完成工作）。它们由同一宿主会话调用或手动切换模型完成，不要求多 Agent 调度。

**「连续性」指三件具体的事**，不是「记得上一轮聊过什么」：

| 连续性 | 要保住 | 失去它会出的问题 |
|---|---|---|
| 研究连续性 | 研究问题、已知证据、尚未解决的解释、下一步需要什么信息 | 换模型后重新讨论已经排除的方案 |
| 实验连续性 | 实验目的、设计、配置、实际进展、结果与产物的对应关系 | 把计划当结果、把最后权重当选中权重 |
| 执行连续性 | 已确认方案、不能改变的定义、工作树状态、最小下一步 | 代码和实验重新搭一套 |

**落地形态**：四种工作方式由**一个 `research-workflow` 技能**承载（`presets/academic-research/skills/research-workflow/`，随预设一起分发，内含决策包与实施卡两个模板）。用户用宿主自带的技能手势 `/research-workflow <场景词>` 显式调用（`dsh-tool-skill` 把技能全文注入当轮；本包不注册命令、不提供工具）。技能内部按**场景**组织（研究梳理 / 实验设计 / 科研实现 / 实验复盘 / 恢复与交接），与本表的工作方式命名**两套并存**，对应关系见该技能的「§零」。技能是提示模板，因此「技能里写了不要擅自跑昂贵实验」只是行为指令，**不是权限隔离**——运行权限仍走宿主的工具与审批管线。

下面两类不要混：带「当前范围」的会随版本推进重新评估（扩展路径见 [`ROADMAP.md`](ROADMAP.md)），带「设计约束」的不随版本改变。

- （当前范围）不新增模型路由、多 Agent 调度、独立实验数据库、归档服务，也不新建跨会话记忆存储。
- （当前范围）不把尚不存在的斜杠命令或工具入口写进文档。工作流入口已在 dsh 0.2.2-rc.1 上确定为宿主技能手势 `/research-workflow`（见 [`ROADMAP.md`](ROADMAP.md) 阶段 2）。
- （当前范围）不做文献爬虫、实验调度平台、知识图谱、自动自我修改规则，也不做按语义判断该淘汰什么的归档系统。
- （设计约束）**压缩不调用模型**（§1）。压缩引擎只负责压缩，工作流模板与研究状态不放进压缩引擎。
- （设计约束）**跨会话连续性走宿主已有的 `dsh-session-reference`**：它对被引用会话生成有界只读快照，并将其标为不可信上下文（禁止遵循其中的指令、权限声明与工具请求）。不另建快照格式，也不把快照当作当前机器状态的替代品——恢复执行仍须核对真实代码与产物。
- （设计约束）**压缩决策保持单一归属**：不得引入第二个 `ctx.compaction` 提供方，也不得再 hook `agent/pre-step`。
- （设计约束）**不引入采用 CC-BY-NC 类许可的第三方内容**。理由：这类许可是「署名 + **禁止商业使用**」，与本包 MIT 不兼容——把其提示词打进本包，等于授予读者一份原作者从未给出的商业许可，加 NOTICE 只能解决署名、解决不了 NC。四种工作方式的提示词**自行编写**。
  已有重新考虑条件：原许可方给出兼容许可，或改为「**只桥接、不打包内容**」的独立包（桥接件在运行时读取本机已有的安装，包内不含第三方内容）。

**高能力模型给出方案 ≠ 方案已经通过实验验证。** 审查意见也是建议，不自动覆盖已确认规格。与现有方案冲突时，把具体条款、调用者和反例交给用户或决策模型；不按审查者名气或模型强弱自动裁决。

### 0.2 优先级

原始记录保真 > 明确事实与判断的边界 > 可以继续执行 > 文本简短与好看。

研究状态记录合并重复叙述，不删掉仍影响当前研究的结果、条件、失败和未决事项。压缩检查点不做这种取舍：它只按规则搬运原话、丢弃并指向工具输出（§1）。

**保真也包括执行语义：哪些对象参与、如何计算、产物代表哪个状态、什么情况下必须停止。** 这些规则记录在研究状态的六节中，不新增一套契约 DSL、任务调度器或代码验证服务。记录保住规则，不等于证明执行代码遵守规则；后者由实际 diff 和少量针对性运行验证。

## 1. 压缩检查点：程序生成，不调用模型

### 1.1 为什么不再让模型写总结

上一版让压缩模型把区段重写成六节交接记录，原文由「模型选来源、程序逐字复制」。真实会话证明这条路不稳，也不够忠实：

- **失败多**：一个真实会话的 13 次压缩只有 2 次成功；失败形态有引用越界、模型把区段当成待继续的任务去调工具、只出 reasoning 不出正文、区段超过模型上下文。失败时会话完全没有压缩，每次耗时 30 秒到 10 分钟。
- **会改写归属**：模型整段重写时，助手的推测可以变成「当前假设」，判断可以被补上 `state: 已确认`（实际发生过）。读者分不清哪句是用户说的。
- **选择不可逆**：模型选中的原文才被保留，选错的会一轮轮带下去；成功的检查点里保留区占一半，多是过程噪音。

同类研究的结论一致：简单丢弃工具输出与模型总结效果相当而成本低得多（JetBrains, *The Complexity Trap*, 2025）；逐字保留用户与助手文字、丢弃工具输出并可按需回查，连续多轮压缩后的事实回忆明显高于模型总结（*transparent-compact*, arXiv 2610.20116）；可恢复的压缩优于不可逆的总结（Manus, 2025）。

### 1.2 检查点的内容

检查点由程序按以下规则生成，顺序固定：

```markdown
本检查点由 dsh-academic-research 按固定规则从会话日志生成，没有调用模型改写。
- （说明：作者归属、未核实、读回方式、规则重新注入、研究状态在哪）

## [rounds] 压缩记录
- 第 1 次：seq A–B，N 条消息；未保留：推理 X 字符，工具输出 Y 字符（Z 次调用），注入上下文 K 条

## [files] 涉及的文件
- /path/to/file（读、改）

## [record] 逐字记录
[用户 · seq 9]
<用户原话，逐字>

[助手 · seq 18]
<助手写给用户的文字，逐字>
- 调用 bash：<该调用自带的 description> → 结果 seq 20（2345 字符，未保留）
- 调用 read：/path/to/file → 结果 seq 22（812 字符，出错，未保留）

[注入 · seq 30] agent-instructions · instructions（未保留）
```

| 区段里的内容 | 检查点里 |
|---|---|
| 用户原话（`source.kind === 'user'`） | 逐字保留，标 `[用户 · seq]`；附件只记数量 |
| 助手文字（text 块） | 逐字保留，标 `[助手 · seq]`；**明确标为未核实**，不是用户确认过的前提 |
| 助手的推理（reasoning 块） | 不保留，只计字符数 |
| 工具调用 | 一行：工具名 + 一句说明（bash 用调用自带的 description，没有就用命令；文件工具用路径；其它用参数，截到 120 字）+ 结果的 `seq`、字符数、是否出错 |
| 工具输出 | 不保留，只计字符数；按 `seq` 读回 |
| 注入的上下文（工作区规则、技能目录、运行时快照、技能正文、goal 轮次等） | 一行出处；notice 类保留它自带的一句说明 |
| 读写过的文件 | 程序从 `read` / `write` / `edit` 调用的 `file_path` 提取，汇总成文件清单（与宿主 `dsh-agent-instructions` 判断文件接触的工具集一致） |

**读回**：每个被丢弃的事件都留下 `seq`。预设挂载 `dsh-tool-session-query`，`session_event_read`（省略 `session_id` 即当前会话）按 `seq` 读回完整事件；宿主以 `openAt: never` 打开查询服务时，只有全文搜索不可用，按 `seq` 精确读取仍可用。也可以重新读文件、重新运行命令。`seq` 指向压缩那一刻窗口里的节点；节点若是替换事件（例如被改写过的工具结果），事件里的 `sourceEventSeqs` 指向原始事件。

**工作区规则不进检查点**：`dsh-agent-instructions` 按会话可见面判断规则基线是否还在，基线被压缩移走后会重新注入（已读 0.2.2-rc.1 源码确认）。

### 1.3 前次检查点

区段里的前次检查点按宿主的 `isCompactCheckpointSource` 识别：

- **本格式**：压缩记录、文件清单、逐字记录分别接上，新内容排在后面；说明头只保留一份，不嵌套。
- **其它格式**（别的后端写的，或本包上一版的六节检查点）：整段逐字作为一条记录携带，标 `[前次检查点 · 其它格式 · seq]`。

### 1.4 能保证什么、不能保证什么

| | |
|---|---|
| **能保证** | 用户原话与助手文字不被改写、不被换作者；没有一条被丢弃的内容是静默丢失的——要么计数，要么留指针；压缩不会因为模型输出出错而失败 |
| **不能保证** | 助手文字里的结论、数值与状态正确；被丢弃的工具输出不读回也能被想起；接手的 agent 会真的去读回 |
| **不声称** | 「研究状态已整理好」——研究状态在 §2 的状态记录里，由写它的人负责 |

### 1.5 已知边界

- **检查点线性增长**。用户原话与助手文字逐字保留，前次检查点整段携带，不设上限。按一个真实会话复算（seq 9–3633，978 个节点、约 41 万 token）：区段 1.72M 字符 → 检查点 87k 字符；再叠一轮后 147k 字符。携带部分最终接近压缩阈值时，基础引擎的「摘要必须小于被压区段」检查会报错，不会静默截断。
- **区段为空、消息对不上会话可见面、前次检查点缺少本格式的分节**：都直接报错，不生成检查点。
- **配置只有基础引擎的键**。上一版的 `domain`、`summaryLanguage`、`recursive`、`chunkMessages`、`domainExtra` 由基础引擎的键校验拒绝（`BasicCompactionConfig: unknown key`），旧配置要删掉这些键。

## 2. 研究状态记录（六节）

研究状态由**工作中的 agent 在事情发生时**写进项目的状态文件（`research-workflow` 技能 §九 的 `.research/STATE.md`，或项目既有位置），也用于阶段交接与决策包。**压缩不生成、不改写这份记录**（§1）。下面的规则约束写这份记录的人——执行模型、决策模型或用户。

### 2.1 六节固定

一份研究状态记录恰有以下六个二级标题，顺序固定：

```markdown
## [goal] 当前目标与假设
## [experiments] 实验台账
## [evidence] 记录与来源
## [analysis] 已有分析与判断边界
## [invariants] 精确保留区
## [open] 待决策问题与下一步
```

`[key]` 固定为 ASCII，不翻译；标题标签和叙述跟随会话语言。不得新增第七节。字段缺值写 `—`，无条目写 `(none)`；两者都不表示“已检查并确认不存在”。

既有 H/E 编号保持不变、不复用。仅给记录里确实存在的假设或实验编号，不为了填模板新增实验。

已有状态记录与新记录合并为一份。不同条件下的旧结果不能被新结果静默覆盖；明确纠正的记录标为“旧值 → 新值，纠正依据”。重复出现的说法不算新增证据。

### 2.2 不得自动补全的内容

没有记录时，不补造单位、不确定度、重复次数、baseline、Δ、显著性、路径、进度、因果解释或结论。

只有“准备运行”不能写“运行中”；有命令不能写“已执行”；进程结束不能写“假设已确认”。看见路径不等于已经读取文件，看见工具输出不等于科研结果已经独立核验。

### 2.3 `[goal]` 当前目标与假设

这一节要让**没看过本会话的人先看懂项目在做什么、这一步推到哪了**，然后才是当前任务。开头两条固定字段（字段键 ASCII）：

```text
mainline: 项目主线——整体目标、当前处于主线的哪一步/哪个条目、该条目的验收标准。
progress: 本次推进——相对上一状态做了什么、到了哪一步、还差什么。
```

`mainline:` 以项目权威文件为准（如 `docs/MAINLINE.md`、`ARCHITECTURE.md`），**保留出处路径与所处条目编号**，只摘当前相关部分，不复制整份规范；原文没有就写 `—`。`progress:` 写成进展汇报而不是待办清单；本次没有推进就写 `—`。**两条都只写原文已有的内容**，不得据推测补全主线阶段或推进幅度。

保留当前研究问题、最新明确任务、交付物和用户的实现约束。不得只记录长远研究目标而漏掉当前要完成的代码或实验任务。

每条已有假设使用：

```text
H<n>：陈述；适用范围；支持/否定判据；状态；依据。
```

判据中的公式、阈值和单位逐字保留；未定义写 `—`。状态保留 `待验证 / 部分支持 / 被否定 / 已确认`，但**记录者不得自行升级状态**。原文已作判断而依据不足时，写“原文判断：……；依据：未溯源”，不代替原作者证明或否定它。

没有正式假设就写 `假设：(none)`。目标或判据是否需要修改，转入 `[open]`。

本项目的代码约束应持续保留：简洁易读、最小必要改动、优先沿用现有实现、不擅改实验口径、不为假设性需求增加框架或大量测试。

已有 MAINLINE、AGENTS.md 或用户指令中的当前适用条款应带出处保留；未提供正文时注明“据输入转述”。只摘实际相关条款，不复制整份规范。任务排除条件必须保留作用阶段，不把“不参与评价”外推为“不参与训练”。

### 2.4 `[experiments]` 实验台账：保留七字段

E 编号是记录标识，不占用字段。编号沿用原记录里的实验标识，**数字或字母都接受**：记为「实验 B」「实验 B2」的写 `EB`、`EB2`，记为 `E3` 的写 `E3`。不重编号、不要求补号——给原文没有号的项目编一个号，等于伪造标识。七个字段键固定为 ASCII，内容可使用会话语言：

| 键 | 标签 | 要求 |
|---|---|---|
| `purpose` | 目的 | 关联 H 编号或明确任务，说明实验要回答什么 |
| `design` | 设计 | 已确定的方法、数据与划分、对照及控制变量；保留各阶段的参与/排除集合和评价口径，未定部分显式写出 |
| `config` | 配置 | 本次实际使用或已确定将使用的关键参数，区分计划配置与实际配置 |
| `status` | 状态 | 计划 / 运行中 / 已完成 / 失败 / 中止；仅保留有记录的进展 |
| `result` | 结果 | 原始指标和条件；尚无结果写 `—`，不把预期结果填进来 |
| `artifacts` | 产物 | 精确路径及角色（选中模型/最后状态/续跑状态等）；已知 epoch、版本及下游读取者一并保留，不从名称猜测；区分预期与已产生 |
| `conclusion` | 结论 | 无判断写 `—`；有判断则标“原文报告已验证 / 推断 / 待判定”，并记录依据 |

结果不统一强制成 `value±err`。按记录实际形态保留：有 `±` 才保留 `±`，已有 SD/SE/CI 定义则一并保留；没有就写“不确定度未记录”，不能补成 `±0`。

baseline 和 Δ 已给出则原样保留；baseline 已给出但 Δ 未给出时，保留两边原值，写 `Δ=—（未计算）`。记录状态时不做新计算；正常实验代码仍可按已确定公式计算指标。不清楚单位或是否可比时，保留原文并列为缺口，不自行解释。

失败原因、已完成阶段、日志、checkpoint、job id 或恢复命令，仅在原记录已有时保留。不把每次代码编辑独立登记为一个实验。

代码修复记录不自动变成一次成功实验。若修复改变标定、评价范围、聚合方式、选中权重或随机配置，已有结果是否需要重算应在 `[open]` 标明“已确定的影响”或“待确认”；既不默认旧结果全部作废，也不默认仍然有效。

### 2.5 `[evidence]` 记录与来源

沿用 `主张或记录 ← 来源`。正式来源仍只分三类：

- 文献：已有 citation key / DOI / arXiv id。
- 实验：已有 `E<n>`，指向台账中的记录。
- 文件：精确路径，附原记录提供的字段、行号或图号。

缺出处写 `← (未溯源)`，不得补造引用。

区分“工具输出记录”“用户报告”“模型意见”；它们是记录性质，不自动构成真实性评级。对话中给出的模型建议不能因附上 E 编号就变成实测事实。会话里的 `seq` 可作为记录的出处说明，但不冒充第四种科研证据。

重要结论的原始来源应随记录保留，不能只剩“上次记录说它是对的”。文件内容未提供时，只保留路径和可见描述，不假装读过文件。

### 2.6 `[analysis]` 已有分析与判断边界

本节是**已有分析的交接区，不是记录者的自由推理区**。

使用两个槽位。字段键保持 ASCII —— 机器判定不依赖会话语言，字段周围的叙述跟随语言：

```text
decision:  已提出的行动方案及其当前决策状态，包括尚未确认的建议。
state:     建议 / 已确认 / 已实现 / 已验证 / 已否认（§2.9）。
basis:     该状态的依据；没有来源写 —。
question:  状态为「建议」时必填，指向 [open] 中存在的 Q<n>。
judgement: 解释、分析、推断及其依据，含已有疑点。
```

没有决定时写一行 `decision: (none)`；该空项不要求 `state:` 与 `basis:`，也不为填格式编一条决定出来。

**出现在 `decision:` 里不等于已经获准执行。** 建议只有在后续输入给出确认依据后才能升级状态，并把动作放入 `[open]` 的 `已确定下一步：`。强模型提出过、或被重复写过几次，都不构成升级理由。

有明确记录时保留跨实验关系并点名 E 编号；没有时不强制寻找矛盾、不强制排除替代解释、不强制生成反证条件。

同一指标出现不同数值但实验条件是否一致未知时，只写“记录存在差异，可比性未定”，不直接宣布相互矛盾。

已有“已验证 / 推断 / 猜测”标记原样保留；不要求三层都有内容，记录者不给已有判断重新评级。允许写“推断性结论”，禁止把推断升级成已验证事实。

高能力模型或用户的已有决策写成 `decision:` 条目并把 `state:` 标为 `已确认`，保留决定、理由摘要和已知出处；执行上的下一步放入 `[open]`。记录者不自行声称已经获得高能力模型审核。

已审查但未采纳的建议，保留“不改的理由”，并把当前执行限制放入 `[open]`。不能在下一次更新记录时把“审查建议”改写成“必须修复”，也不能因暂时不支持某分支而补造该分支的实际调用者。

### 2.7 `[invariants]` 精确保留区

保留影响当前实验解释、复现或恢复执行的原文片段，包括：

- 指标、baseline、已记录的 Δ、不确定度、重复次数及其对应实验和条件。
- 公式、单位、阈值、常量与定义。
- 关键配置、代码/数据/模型版本、seed 与确定性设置。
- 配置、结果、checkpoint、日志、原始数据的精确路径；必要的报错和恢复命令。

**优先保留带上下文的原始行或小段，不只摘出裸数字。** 数值必须仍能对应到原实验、指标和条件。禁止四舍五入、单位换算、符号替换、公式化简和路径改写。

**只摘带实验归属、指标或必要条件的片段，宁少勿多。** 取材优先级：① 执行契约（范围与顺序、计算定义、产物身份、执行边界）② 带实验归属的原始数值与条件（H/E 编号 + 指标名 + 单位 + 对照 + 运行条件）③ 报错串、恢复命令、精确路径 ④ 本身即契约的代码（带文件路径与角色）。寒暄、确认、「请你 review」这类对话不摘。

**每段摘录逐字复制并写明出处**：会话里的 `seq`（用户原话注明是用户说的），或文件路径与行号。按出处由程序核对摘录是否逐字一致，是后续工作（[`ROADMAP.md`](ROADMAP.md) 阶段 3）；在此之前，摘录是否与原文一致没有程序保证，读者要回原处核对。

保留区不是全部日志的副本。重复中间输出可以压缩；但仍被分析、调试或下一步决策引用的记录不得删除。不能以“路径还在”替代从未实际保存过的原始内容。

当前任务已有以下**执行契约**时，同样保留其原文与适用范围；无关项不展开，不凭模板补全：

- 范围与顺序：训练/开发/评价各用哪些任务，排除哪些；评价臂固定顺序及 baseline 的明确身份。
- 计算定义：目标函数、阈值比较符、平局规则；聚合对象、权重、分母与去重规则；对照差的方向。
- 产物身份：产物名或路径对应选中 epoch、最后 epoch 还是续跑状态；下游实际读取哪个产物。
- 执行边界：实际进程分工、共享文件的写入者与同步条件；缺关键数据、状态不一致时的既定停止规则；seed 的角色和已要求的约束。

只保留已有定义，不新增统一配置系统。特别是缺少目标函数、比较符或平局定义时，把算法问题交给决策方，不允许仅凭一个失败样例拼补候选点后宣布算法正确。

### 2.8 `[open]` 待决策问题与下一步

按需要记录四类内容，不强制每类都有条目：

1. 已确定、可以执行的下一步：目标、最小实施动作、必须不变的条件和验收方式。
2. 待决策问题：交给用户或高能力模型，不由记录者代答。
3. 阻塞项：明确缺少的数据、权限、算力、接口或参数。
4. 已否决方案：方案、原有否决理由、已有重启条件；不能编造永久禁止条件。

待决策问题使用以下紧凑数据包：

```text
Q<n> · 问题：究竟需要决定什么？
依据与缺口：相关 E 编号、关键原值或 `[invariants]` 中的摘录；缺少哪些信息。
需要的答复：例如确定对照、解释差异、选择下一步实验；不预设正确答案。
执行边界：哪些既定任务仍可继续，哪一步需要等该问题解决；原文未定则写 —。
```

无需凑够固定数量的问题，也不要求模型提供候选方案、优先级评分或推荐答案。可以根据显式缺字段、执行报错、要求冲突或用户已有疑问形成问题；不得制造“有深度”的问题。

问题获答后记录决定及出处，把明确动作转入可执行项。只有涉及科研有效性或改变既定方案的歧义才需要升级决策；普通命名、函数拆分等工程细节由执行模型按简洁原则处理。

代码修改期间，再用普通条目交接以下实际状态；这些条目是 §2.9 状态词升级所需的依据来源，不新增第八个实验字段：

```text
工作树：是否未提交；基准 commit、修改文件及 diff 定位有记录则保留，否则 —。
处理：哪些条目报告已改、已删或未采纳；谁报告的。
验证：实际运行过的命令、观察结果与未覆盖项；未提供证据不等于“没有验证过”。
产物影响：哪些既有结果/模型需重算或复核；没有决定则列为待决策。
```

**报告已修 ≠ 已查看当前 diff ≠ 回归通过 ≠ 正式重跑完成；提交状态另行记录。** 不把工作树改动归到旧 commit，也不因交接需要擅自提交、覆盖产物或重跑昂贵实验。被拒绝的修法，按“建议 → 未采纳原因 → 当前处理 → 已有重新考虑条件”保留；没有新依据时不重复尝试。

### 2.9 阶段状态词表：不新增状态机，但要能区分建议与已验证

同一内容会经历 `提出建议 → 确认方案 → 实现代码 → 运行实验 → 得到结果`。这些阶段**可以变化，但不得发生身份偷换**：把建议写成已确认、把已实现写成已验证，是交接失效的首要原因，也正是 §0.1 验收重点要拦住的东西。

要求：`[analysis]` 中记录的决定、`[open]` 中的已确定动作与已否决方案，各自带一个状态词，取值**仅有五个**。`Q<n>` 待决策项**不需要**状态词——它本身就是「尚未决定」的记录格式（§2.8）：

| 状态词 | 含义 | 升级所需的记录 |
|---|---|---|
| `建议` | 有人提出，尚未被确认 | 提出者与出处 |
| `已确认` | 用户或决策模型已明确同意执行 | 谁确认的、在哪条记录里 |
| `已实现` | 代码或配置已按确认方案改完 | 改了哪些位置；**不等于已提交，也不等于已运行** |
| `已验证` | 已有实际观察支持它成立 | 哪次运行、哪个产物、哪次读取；**不认「报告已修」** |
| `已否认` | 已明确不采纳，或被实验否定 | 否决理由与已有重启条件 |

规则：

- **升级只认记录，不认语气。** 没有写出依据时不得升级状态，保持原状态并写 `依据：—`。
- `已确认` 只能由用户或决策模型的明确表述产生，记录者不得自行认定；依据写到那条表述的 `seq`。
- `已实现`、`已提交`、`已验证` 是三件事，分别记录；工作树未提交时，`已实现` 条目必须同时保留未提交状态。
- 既有产物是否受某次改动影响，属于 `[open]` 的待决策项，不得写成 `已验证`。
- 研究评议产生的新判断作为**新条目**加入 `[analysis]`，不得回头修改已逐字摘录的原始结果。

**这不是状态机。** 不定义转移、不自动推进、不新增校验引擎；它只是五个词的封闭取值，加一条「升级须凭证据」的记录规则。

**写法**：状态只挂在 `[analysis]` 的**非空 `decision:` 条目**上；解释留在 `judgement:`，不带这套状态；`[open]` 保留 `已确定下一步：`、`Q<n>`、`已否决方案：`，**不重复维护决策状态**。也不得把这五个词套到 `[experiments].status` 或 `conclusion` 上——实验是否运行、方案是否确认、结论是否验证，是三件不同的事。

格式要求三条：`[analysis]` 必须出现 `decision:`，没有决定时写 `decision: (none)`；每条非空 `decision:` 带 `state:`（五词之一）与 `basis:`，无来源时 `basis: —`；`state: 建议` 的条目用 `question:` 指向 `[open]` 中存在的 `Q<n>`。

**格式合规只说明写法对**：不说明状态与原始证据一致，更不构成执行授权。`basis:` 是记录者写的依据，不是程序核实过的确认。

## 3. 研究状态的保留规则

**不使用“最近 N 条”作为删除研究状态的唯一依据。** 以下仍与当前任务有关的内容必须保留：运行中实验、尚未完成的已确定计划、当前 baseline、支撑或反驳当前假设的关键实验、未解决失败、阻塞及待决策问题。

重复讨论、未采纳的泛泛设想、没有继续用途的过程叙述可以合并。历史结果不再详细展开时，仍保留当前研究需要的关键值、条件与来源。不新增归档服务，也不声称不存在的完整台账会兜底。

## 4. 执行模型：最小改动，不省略真实正确性条件

写代码前，仅就将修改的部分确认“规格原文 → 实际调用点 → 最小反例/验收观察”。正常命名和局部结构自行处理；规格冲突、优化目标、聚合口径或模型选优含义不明时，先带相关代码片段提问，不猜。

同一概念沿用同一份定义：任务集合、臂顺序、baseline 身份、选中 epoch 和产物出口，不在不同函数中另写略有差异的副本。已有配置为唯一来源时继续使用它；不为统一而新建配置平台。

“少防御性编程”不删真实约束：缺必要组不能静默跳过；已要求的 seed/臂序约束在昂贵运行前检查；两个进程实际共享文件时必须处理写入归属和完整发布。原子发布只解决半文件，不替代进程身份与真实同步。不要为不存在的调用者增加支持分支，不新增无限重试、自动修复或静默回退。

真实故障的验证优先用小输入或短运行，按实际修改选择，不给所有任务强制分配测试数量：数值/排序问题用微型反例；评价范围和聚合用能看清成员、权重与分母的小输入；产物选择沿真实下游入口回读；并发问题做短的双 worker 冒烟。昂贵训练不能替代这些检查，单次冒烟也不能证明不存在并发故障。

测试服务已知反例与当前调用链，不建设大规模兼容矩阵。删除死分支、重复存储、整份大对象打印；保留复现所需的精简配置、seed、选中 epoch、结果摘要和产物定位。交付时说明修改、实际验证及未验证项，不用“已修”概括所有状态。

## 5. 研究状态记录示例（M1）：按报告记录，不冒充复审

下面仅示范如何携带用户本次提供的修复报告。它不是插件对所有项目的硬编码模板，不包含 M1 源码。报告称已回代码逐条核实；本文没有取得这些代码与验证输出，也不能从未提交推断没有测试。D 编号沿用问题记录，不伪造 E 编号；未知路径、任务名、固定顺序和权重不补造。状态词按 §2.9 标注，用以示范「已实现 ≠ 已提交 ≠ 已验证」以及「建议 ≠ 已确认」。

## 6. 定稿决定

- **压缩不调用模型**：检查点由程序生成，原话逐字、标明作者、丢弃的内容留 `seq`（§1）。
- **研究状态不由压缩生成**：六节记录由工作中的 agent 在事情发生时写，压缩只搬运会话原话（§2）。
- **跨会话连续性复用宿主的 `dsh-session-reference`**，不另建快照格式（§0.1）。
- **决定、已确定动作与已否决方案带 §2.9 的五个状态词之一，升级须写出依据**；`已确认` 的依据指向用户那条表述的 `seq`。
- **产品目标为研究连续性，但工作流模板与研究状态不进入压缩引擎**（§0.1）。

**验收重点：一个没有看过完整历史的新会话，能从检查点分清哪句是用户说的、哪句是助手说的，能按 `seq` 读回被丢弃的工具输出；能从研究状态记录准确区分已确认方案与建议、已实现与已验证，并在不重新猜测科研定义的前提下完成下一项任务。**

**工作流验收**：用一个真实研究问题完成一次 `材料整理 → 强模型决策 → 小模型最小实现 → 记录结果 → 换会话继续`。只验证这一条闭环，不扩成大型评测工程。
